## 1. Контекст и проблема

### 1.1. Два переводчика стратегии, которые расходятся
Стратегия пользователя строится из Blockly-блоков и хранится как `strategy_versions.blocks_json`. Сегодня логика стратегии переводится в исполняемый код **дважды, двумя независимыми переводчиками под два разных рантайма**:

| | Бэктест | Live / sandbox / paper |
|--|--------|------------------------|
| Переводчик | `app/strategy/code_generator.py` (+ `block_parser.py`) | `SignalProcessor._blocks_to_sandbox` (`app/trading/engine.py`) |
| Результат | backtrader-класс `GeneratedStrategy(bt.Strategy)` (хранится в `generated_code`) | sandbox-скрипт `print("buy"/"sell"/"hold")`, исполняется в RestrictedPython |
| Грамматика | **полная** (8 индикаторов, compare/crossover/in_zone, logic and/or/not, management, filter_time) | **урезанная**: только SMA/EMA/RSI и `condition_compare` с числом справа |

**Ключевой факт:** в live backtrader-код `generated_code` НЕ исполняется — движок видит `class GeneratedStrategy` и перегенерирует стратегию из `blocks_json` своим урезанным переводчиком ([engine.py:478-486](../../Develop/backend/app/trading/engine.py#L478-L486)).

### 1.2. Следствие — backtest ≠ live
Что live-переводчик игнорирует: `condition_in_zone`, `condition_crossover`, `logic_and/or/not`, сравнение индикатор-vs-индикатор, индикаторы MACD/BB/ATR/Stochastic/Volume, несколько условий.

Конкретно для версии sv=92 (стратегия из инцидента): exit построен на `condition_in_zone` (EMA в зоне 30–70) → live-переводчик выдаёт `exit_sig = (False)` → **пользовательский выход никогда не срабатывает в live**, хотя в бэктесте работает. Шире — любая стратегия с этими фичами в live ведёт себя не так, как показал бэктест, **молча**.

> Важно: SL/TP риск-менеджмент в live это НЕ затрагивает — он идёт отдельным путём `_attach_sl_tp` → `extract_risk_params` → `RiskMonitor` и работает корректно (проверено на sv=92: SL 3% / TP 6%). Речь именно о **сигналах входа/выхода**, формируемых логикой стратегии.

### 1.3. Вторая, независимая проблема — поток 1m-свечей молча умирает
gRPC-мультиплексор T-Invest (`app/broker/tinvest/multiplexer.py`) переподключается **только при исключении**. При «вежливом» закрытии стрима сервером цикл `async for response in market_data_stream(...)` завершается без исключения → фоновая задача `_run_stream` выходит → реконнекта нет, keepalive не шлётся → слушатель сессии вечно висит на `queue.get()`. Это объясняет остановку свечей сессии #5 на `2026-06-04 10:19` (~11 мин после старта) без возобновления.
**Статус причины:** гипотеза из чтения кода, **не воспроизведена**. Подсистема отдельная от §1.1–1.2.

## 2. Цели и не-цели

### Цели
1. Live и бэктест принимают **одинаковые торговые решения** на одной и той же истории свечей (поведенческая эквивалентность сигналов).
2. Live поддерживает **всю** грамматику блоков (как бэктест), а не урезанную.
3. Пользователь **видит** в результатах бэктеста, что live-движок согласуется с бэктестом.
4. Поток рыночных данных не «умирает» молча: разрыв (в т.ч. graceful close) → авто-реконнект.

### Не-цели
- Замена backtrader как движка бэктеста (его симуляция брокера, комиссии, OCO-ордера SL/TP, метрики — остаются).
- Удаление `generated_code`.
- Переписывание position sizing с формы сессии на блоки (остаётся как есть — форма главнее).

## 3. Принятые решения (зафиксированы с заказчиком)

1. **Подход — общий интерпретатор + differential-сверка в бэктесте** (вариант пользователя, сильнее «by construction», ниже риск):
   - В **live** работает интерпретатор `evaluate(ir, candles)`.
   - В **бэктесте** основным остаётся backtrader(`generated_code`); интерпретатор гоняется **shadow-прогоном** по той же истории, и его решения сверяются с backtrader.
2. **`generated_code` не удаляем.** Он остаётся: оракулом сверки в бэктесте, артефактом для показа в UI, основой правки параметров, fallback-источником SL/TP для AI-стратегий. `blocks_json` (IR) — источник истины для **исполнения**.
3. **Что сверяем:**
   - **Сигналы/сделки** (бар входа/выхода + направление) — расхождение **критично = блокер**.
   - **Итоговые метрики/P&L** — **информационно**: показываем, в чём и (по возможности) почему расходится. Не блокирует.
4. **Гейт live:** при критичном расхождении запуск live для этой версии **блокируется**, но с возможностью **явного override + подтверждения** пользователем. Если по версии ещё нет бэктеста со сверкой — live **жёстко блокируется** (override НЕ предусмотрен): сначала нужен бэктест со сверкой. *(решение заказчика 2026-06-10)*
5. **Поток свечей:** сначала **подтвердить причину** (логи/инструментация/наблюдение), затем фикс. Отдельный цикл (SP-B).
6. **Рамки:** всё в Sprint 8 Review.
7. **Правка параметров** (`replace_strategy_params` / `extract_strategy_params`) мигрируется с текста `generated_code` на IR (`blocks_json`) — **в этом же спринте**. *(решение заказчика 2026-06-10)*

## 4. Архитектура

### 4.1. SP-A. Новые модули

```
app/strategy/indicators.py     # ОДНА каноничная реализация каждого индикатора (сериями)
  sma, ema, rsi, macd, bollinger, atr, stochastic, volume
  - вход: списки close/high/low/volume; выход: серия значений (None на «прогреве»)
  - конвенции ВЫРОВНЕНЫ под backtrader (см. §6 — RSI Уайлдер!)

app/strategy/evaluator.py
  parse_blocks(blocks_json) -> StrategyIR        # нормализация хранимого формата Blockly
  evaluate(ir, candles) -> "buy" | "sell" | "hold"
    - считает нужные индикаторы через indicators.py
    - вычисляет entry/exit условия:
        compare (число и индикатор справа), in_zone, crossover (нужны 2 бара),
        logic and/or/not, indicator-vs-indicator
    - комбинирует с signal_entry.DIRECTION / signal_exit
```

`evaluate` заменяет связку `_blocks_to_sandbox` + RestrictedPython для блочных стратегий.
**Бонус безопасности:** блочную стратегию теперь *интерпретируем как данные* доверенным кодом, а не исполняем сгенерированный текст в песочнице.

### 4.2. SP-A. Live-путь
- `runtime._handle_candle` вызывает `evaluate(ir, candles)` на каждой закрытой свече вместо `SignalProcessor._blocks_to_sandbox`+sandbox. Downstream (`Signal`, `OrderManager`, `RiskMonitor`) — без изменений.
- **IR-less стратегии** (в БД нашлась 1 версия: пустой `blocks_json`, но есть `generated_code`): для них интерпретатору нечего интерпретировать → **legacy-fallback** (сохраняем прежнее поведение / помечаем как не-live-capable). Это явный edge, не блокер основного потока (88/91 версий имеют реальное дерево блоков).

### 4.3. SP-A. Бэктест: dual-run + сверка
1. Backtrader(`generated_code`) исполняется как сейчас → `backtest_trades` + метрики (ОСНОВНОЙ результат, не трогаем).
2. Интерпретатор гоняется shadow-прогоном по той же истории свечей: для каждого бара `i` решение из серий индикаторов (O(N), серии считаем один раз) → список `(бар, buy/sell)`.
3. **Сверка сигналов:** список интерпретатора нормализуется и сравнивается с `backtest_trades` (оракул backtrader).
   - **Поправка на исполнение backtrader:** ордер исполняется на открытии *следующего* бара после решения в `next()`. «Бар решения интерпретатора i» ↔ «бар входа backtrader i+1». Нормализуем, иначе ложное расхождение на 1 бар.
   - Сравниваем: бар входа, бар выхода, направление. Любое несовпадение = **критичное расхождение**.
4. **Сверка метрик:** итоговый P&L и ключевые метрики (интерпретатор считает свой P&L по тем же fill-правилам, что доступны) → **информационно**: diff показываем, не блокируем.

### 4.4. SP-A. Гейт live
- Запуск live-сессии (`SessionStartRequest`) для версии стратегии проверяет результат сверки последнего бэктеста этой версии:
  - сигналы совпали → разрешаем;
  - критичное расхождение → **блок (4xx)**, если не передан явный `override_parity=true` + подтверждение; факт override пишем в `audit_log`.
- Если по версии **нет** бэктеста со сверкой → запуск live **жёстко блокируется** (4xx, override недоступен): сначала требуется прогнать бэктест со сверкой.

### 4.5. SP-B. Поток свечей (после подтверждения причины)
- **Фаза 0 (подтверждение):** найти серверный лог (structlog→stdout uvicorn) и грепнуть `multiplexer_disconnected/_connected/_cancelled` вокруг `10:19` 04.06; либо инструментировать `_run_stream`/`_request_iterator` и понаблюдать в рыночные часы. Цель — доказать «graceful close без реконнекта».
- **Фаза 1 (фикс, если подтвердилось):**
  - детектировать завершение `async for` без исключения → трактовать как разрыв → reconnect + `_resubscribe_all`;
  - периодический keepalive/ping в `_request_iterator`, чтобы сервер не закрывал по idle;
  - (опц.) watchdog по `last_event_at` — нет свечей дольше порога в рыночные часы → форс-реконнект.

- **Результат бэктеста** (`backtests`/`backtest_jobs` + схема ответа): добавить поля сверки:
  - `parity_checked: bool`
  - `parity_signals_match: bool` (критичный флаг для гейта live)
  - `parity_divergences: json` — список `{bar, backtrader, interpreter}` для показа

  - Alembic-миграция.
- **Гейт live:** override фиксируется в `audit_log` (новый `event_type`). Передача `override_parity` — поле в `SessionStartRequest`.
- **UI:** в результатах бэктеста — бейдж «live-движок: ✅ совпадает / ⚠️ расхождение на N барах» + детализация; при запуске live — предупреждение/подтверждение при override.
- `generated_code`, `blocks_json` — без изменений структуры.

## 6. Краевые случаи и риски

1. **Расхождение математики индикаторов — ожидаемо на старте.** Сейчас `calc_rsi` использует простое среднее, а backtrader RSI — сглаживание Уайлдера (SMMA) → разойдутся. SMA/EMA совпадают. **План:** `indicators.py` пишем по конвенциям backtrader; parity-юнит-тесты `indicators.py` vs `bt.indicators.*` гоняем до зелёного; где совпасть нельзя — фиксируем и пере-базируем осознанно. Differential-сверка — это в т.ч. инструмент достижения паритета.
2. **Бэктест-метрики могут чуть сдвинуться?** Нет — backtrader-исполнение бэктеста НЕ меняем; интерпретатор только добавляется рядом для сверки. Существующие метрики стабильны.
3. **Формат `blocks_json`.** Хранимый формат — сериализация Blockly-workspace (вложенные `inputs`/`next`), а не «плоский IR» из `block_parser`. `parse_blocks` обязан принимать **хранимый** формат (как это делает текущий `_blocks_to_sandbox`). Привести к единому внутреннему `StrategyIR` — конкретная задача плана.
4. **IR-less / AI-стратегии.** §4.2 — legacy-fallback; для SL/TP сохраняется `extract_from_generated_code`.
5. **Стоимость shadow-прогона** в бэктесте — лишний O(N) проход; не горячий путь, приемлемо.
6. **Смысл расхождения.** Live всегда исполняет по интерпретатору (внутренне consistent) — стратегия «применима». Но при расхождении бэктест перестаёт честно предсказывать live → именно поэтому сигнальное расхождение блокирует live. Расхождение не говорит «кто прав» — расследуем и выравниваем до нуля.
